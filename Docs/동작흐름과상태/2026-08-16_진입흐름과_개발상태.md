   **Meta-Labeler**다 — 2026-08-16 리허설 실측 `n_experts=0` 갈래 `{blocked_by_meta: 15/15}`.
4. **그런데 그 Meta 거부의 뿌리는 레이블에 있다.** 2026-08-16 재측정 — 30m은 flat 76.3%라
   `|S|` 천장이 0.237로 게이트 0.20에 여유 1.18배뿐이고, **6개 Horizon 전부에서 비용 강등

   모델이 못 배운 게 아니라 **가르친 것이 "거의 아무것도 거래하지 말라"였다.**

## 1. 전체 경로

```
[L1] KIS WS 틱 ──> TickCollector ──> BarComposer ──> bar.{h}.{symbol}
                                                         │
[L2]                                    FeatureEngine ───┴──> feat.{h}.{symbol}
                                                         │
     RegimeRuntime ──(bar.30m)──> RegimeAI.classify() ──> intel.regime
                                                         │
[L3]  FuturesAIService ──────────────────────────────────┘
        ├ HorizonExpert.predict()      (LightGBM ×5 앙상블 → p_up/p_flat/p_down, ens_std)
        ├ MetaLabeler.passes()         (meta_passed 덮어쓰기 = "지금이 배팅할 때인가")
        └ Aggregator.compute()         (Regime 가중 통합 → S) ──> intel.futures
                                                         │
[L3.5] TradingPipeline.handle_futures_view() ────────────┘
        ├ ① CircuitBreakerMonitor.observe()   (정지/해제 판정, sys.circuit_breaker 발행)
        ├ ② KillSwitch.evaluate()             (발동 시 halt + 전량 EMERGENCY 청산)
        ├ ③ MetaDecisionEngine.decide()  ──> decision.intent  (NO_TRADE도 항상 발행)
        ├ ④ 정규장 게이트                      (판단은 하고 주문만 생략)
        ├ ⑤ ATR 워밍업 + CostModel → Net Expected Return
[L4]    ├ ⑥ RiskEngine.evaluate()             (거부권 — 항소 불가)
        └ ⑦ PositionSizer.size()              (VolTarget × 1/4 Kelly × (1−u))
                                                         │
[L5]  OrderGateway.submit() ─────────────────────────────┘   ← 시스템 유일의 주문 경로
        pending 원자 등록 → broker.submit() → 실패 시 롤백
```

- 프로세스 간 통신은 **전부 Redis Bus**(직접 함수 호출 금지, SYSTEM.md §4-2)
- 실제 배선처: `scripts/run_g2_paper_trading.py` (L1 발행자는 `scripts/run_l1_daily.py`)
- 이 프로세스는 **자체 WS 연결을 열지 않는다** — 같은 계좌로 WS 2개를 열면 서로 반복
  단절(2026-07-23 실측, capability_matrix). 대가는 L1 발행자가 살아 있지 않으면 이 경로가
  아무 신호도 못 받는다는 것.
- **`intel.regime`이 이 그림에 새로 들어왔다.** `RegimeRuntime`은 `feat`가 아니라 `bar.30m`을
  구독한다 — `RegimeAI.classify()`가 FeatureVector가 아니라 `BarClosed` 시퀀스를 직접 받는
  설계이기 때문(국면 관측치와 Expert 피처는 서로 다른 재료를 쓴다).

## 1.5 기동 — 웜스타트 (2026-08-16 갱신, 08-06판에 없던 절)

**이 절이 새로 생긴 이유**: 08-06 이후 하루를 통째로 잃은 사고 넷 중 셋이 여기서 났다.

### 왜 필요한가 — 산술이 그렇다

`FeatureEngine`은 매 기동마다 빈 `deque`로 출발했다. 요구 봉 수는 **측정값**이고
(`px_ema_cross_60`=180 · `px_macd_h_60`=139 · `vl_vov_120`=126), 하루가 만드는 봉은
Horizon마다 다르다:

```
BARS_PER_SESSION  1m 410 · 3m 137 · 5m 82 · 10m 42 · 15m 28 · 30m 15   (실측)

웜스타트 0봉에서 180봉까지 → 1m 1거래일 · 3m 2 · 5m 3 · 10m 5 · 15m 7 · 30m **12거래일**
```

국면은 별도 축이다 — `RegimeAI.classify()` 하한은 **22봉**인데 30m은 하루 15봉이라
**웜스타트 없이는 장 마감까지 단 한 번도 하한을 못 넘는다.** 2026-08-12 실측으로 그날
판단 14건이 전량 `Regime=UNKNOWN` → `NO_TRADE`였다. 국면이 분포가 아니라 상수였다.

> **두 축을 섞지 말 것.** "롤 비용 2거래일"은 국면 하한 22봉 이야기이고, 피처 완전성은
> 12거래일이다. 2026-08-14에 이 둘이 같은 말로 섞여 있었다.

### 어떻게 채우나

```
backfill.warmstart_symbol_chain(symbol, day)      → ['A05609', 'A05608']  (롤 경계 대비)
ParquetArchiver.load_recent_bars_by_source(chain) → 봉 + 심볼별 출처(bars_by_source)
FeatureEngine.warm_start(history, accept_symbols=chain, prev_day_close_ticks=...)
RegimeRuntime.warm_start(bars30, accept_symbols=chain)
```

세 가지 규율이 코드에 박혀 있다:

1. **이어 붙인 봉의 `symbol`은 바꾸지 않는다** — 직전 월물 구간은 그 월물 코드를 그대로
   달고 나간다. 요청 심볼로 덮어쓰면 "이 구간이 어디서 왔나"를 아무도 알 수 없다.
   `bars_by_source`가 함께 로그에 남는다(R10 — 조용히 잇지 않는다).
2. **적재 필터는 체인을 명시적으로 받는다**(`accept_symbols`) — 없애지 않았다. 남의 심볼이
   섞이는 것에 대한 마지막 방어선이므로, 없애는 대신 **무엇을 허용하는지 말하게** 했다.
3. **로더가 건넨 양과 적재된 양을 매 기동 대조한다**(`backfill.audit_warm_start_drop()`) —
   다르면 `WarmStartBarsDropped`(WARNING).

### 3번 규율이 생긴 이유 (2026-08-16 P0)

1번과 2번이 **서로 모순인 채로 이틀간 배포돼 있었다.** 로더는 직전 월물 봉을 그 코드
그대로 돌려주는데 적재 필터는 `b.symbol == self._symbol` 하나였다 — **전량 버렸다.**

```
로더:  30m 200봉 (A05609 15 · A05608 185)
적재:  30m  15봉  < 하한 22봉   →  UNKNOWN 개장 확정
```

거짓말한 코드는 없었다. 두 함수 다 "적재된 봉 수"를 정직하게 돌려줬다. 문제는 **아무도
두 수를 나란히 놓지 않았다**는 것이다 — 자가점검이 보고한 `직전 25일`은 **로더의 답이지
적재된 양이 아니었고**, 두 수가 다를 수 있다는 것을 몰랐다. 수정 후 전 Horizon 200봉 ·
국면 `TREND_DOWN`(0.999).

### 웜스타트의 세 소비처

| 소비처 | 무엇을 채우나 | 없으면 |
|---|---|---|
| `FeatureEngine.warm_start()` | Horizon별 롤링 윈도(용량 200봉) + `SessionState`(전일 종가) | 1m NaN 84.7%로 개장, 30m은 종일 |
| `RegimeRuntime.warm_start()` | 국면 이력 버퍼(하한 22봉) | 종일 `UNKNOWN` → 판단 전량 NO_TRADE |
| `_seed_preopen_reference_price()` | 옵션체인 ATM 기준가 | 장전 10사이클 스킵 — **소급 불가라 영구 결손** |

**알려진 한계 — 롤 점프는 보정하지 않는다.** 이어 붙인 지점에 월물 간 basis가 그대로
들어온다. 2026-08-14 경계 점프 **1990틱**(같은 창의 일자 경계 갭 13건은 중앙 817 · 최대
3160틱이라 범위 안), 과거 7개 롤의 basis 중앙 116 · 최대 240틱만큼이 인공물이다. 이번
롤은 겹침이 없어 **측정조차 못 했다**(`matched_minute=None`). 구조 해법은 G-1(롤 D-1
사전 백필)이고, 여기서 보정하면 원본과 조정본이 뒤섞여 되돌릴 수 없다.

## 2.4 호라이즌별 피처 배정 — 여전히 없다

> **6개 Horizon 전부가 완전히 동일한 137개 벡터를 받는다.** Horizon별로 다른 `feature_set`을
> 주는 배선 자체가 존재하지 않는다.

배정표(Ver 1.5 §3)가 구현 불가인 이유는 단순하다 — **배정의 주력 재료가 없다.** 1m의
65%(MS), 30m의 40%(OP+RG)가 통째로 부재라 배정표대로 자르면 1m은 남는 게 30%뿐이다.

**그럼 Horizon 간 차이는 어디서 오나 — 두 곳뿐**

① **윈도우 단위가 "해당 Horizon의 봉 수"다**:

| 피처 | M1 | M5 | M30 |
|---|---|---|---|
| `px_mom_20` | 20분 | 100분 | **10시간** |
| `px_hurst_120` | 2시간 | 10시간 | **60시간(≈5거래일)** |

② **레이블이 다르다** — 배리어 폭 0.5 → 2.0 ATR, Horizon별 완전히 별개 모델.

즉 **"6개 전문가"는 지금 "같은 재료를 6개 시간 해상도로 본 6개 모델"**이지, 설계가 말하는
"재료가 다른 6명의 전문가"가 아니다.

## 2.5 완성봉 → FeatureVector

`bar.{h}.{symbol}` **완성봉**을 받은 시점에만 계산·발행(완성봉 규율, 유예 500ms).
히스토리 상한 `_MAX_HISTORY = 200`봉.

계산 불가(워밍업 미달·표본 부족)는 **`None`으로 마킹**하고 0으로 채우지 않는다 — 0으로
채우면 "평균과 같다"는 없는 사실을 주장하게 된다. `nan_ratio`가 벡터에 함께 실려 나간다.

**세 번의 사고가 이 규율을 만들었다**:

- `deque` 슬라이스 미지원으로 계산기 대다수가 `TypeError`를 던지고 `_safe_call`이 조용히
  None으로 삼켜, 80봉 워밍업 후에도 **82개 중 72개가 항상 NaN**이었다(2026-07-26).
- `px_ema_cross_60`(180봉)·`px_macd_h_60`(139봉)이 당시 상한 130을 넘어 **프로덕션에서 항상
  NaN인 채로 학습**되고 있었는데, 매일 찍히는 `nan_ratio=0.0165`가 "정상"으로 읽혔다
  (2026-08-04 → 상한 200).
- **퇴화 검사가 표본 부족 Horizon을 "정상"이라고 말했다**(2026-08-14 F-C). 임계 30봉 미만은
  판정이 구조적으로 불가능한데 `FeatureHealthSummary "퇴화 0건"`이 나갔다 — 가장 위험한
  30m(14표본)이 가장 안심되는 문장을 받았다. 지금은 `judged: bool`로 갈라
  **"검사된 0"과 "검사 안 된 0"을 다른 태그로** 낸다.

## 2.6 Expert → 방향 확률

```
FeatureVector.values (dict, None=NaN)
   ↓ feature_row()  — 학습 시점과 동일한 정렬 순서 (train/predict 공유 유일 경로, 계명 6)
   ↓ LightGBM ×5   (seed만 다른 동일 하이퍼파라미터)
member_probs [5 × 3]
   ↓ ens_std = P(+1) 5개의 표준편차              ← 불확실성 원료
   ↓ mean(axis=0) → ProbabilityCalibrator(Isotonic, 선택적)
p_down / p_flat / p_up  +  top_features(gain 상위 5)  +  valid_until
```

- LightGBM은 NaN을 네이티브로 처리(결측 자체가 분기 정보)
- 클래스 매핑 `{-1:0, 0:1, +1:2}`는 모듈 상수 고정 — 바꾸면 저장 모델과 어긋난다(L25)
- `meta_passed`는 여기서 **항상 True**. 실제 판정은 §2.7

**2026-08-16 실측 — 1차 모델이 `p_flat`에 쏠려 있다.** 08-14 재생 30m 15사이클에서
`p_flat` 0.473~0.967, `p_up` 최대 0.438. 즉 **Meta 이전에 Expert 자체가 방향 확신을
거의 안 낸다.** §2.10의 천장 문제와 직결된다.

## 2.7 MetaLabeler → "지금이 배팅할 때인가"

1차 모델은 "어느 쪽인가"에 강하고 "지금이 때인가"에 약하다 — 역할을 분리해 **승률 필터를
독립적으로 학습**한다. 얕은 LightGBM(depth ≤ 4, leaves ≤ 15) — "필터는 단순해야 필터답다".

메타 피처는 설계상 8종이나 **지금 낼 수 있는 5개**만 쓴다:

```
meta_p_primary · meta_margin · meta_ens_std · meta_realized_vol · meta_minutes_since_open
```

(Regime·스프레드·이벤트 근접도는 부재. `meta_realized_vol`은 `px_bb_width_20` 재사용.)

- **임계값 선택**: 정확도 최대화가 아니라 **비용 차감 후 기대수익 최대화** 그리드서치
- **Look-ahead 방지**: `PurgedKFold` out-of-fold 예측을 입력으로 씀(구조적 강제)
- 결과가 `meta_passed`를 덮어쓰고, **False면 그 전문가는 집계에서 완전히 제외**(가중치 ×0)
- MetaLabeler가 없는 Horizon은 필터링 없이 통과 — 배관을 안 끊기 위한 선택

### ★ 지금 진입을 막는 것이 바로 여기다 (2026-08-16 실측)

live 번들 `real-20260811-1604-30m`의 임계는 **0.7**. 08-14 재생 15사이클 통과확률:

```
최소 0.0175 · 중앙 0.0295 · 최대 0.6576      →  임계 0.7 통과 0/15
```

**구조적 0이 아니라 근소한 미달이다.** 그리고 이 임계는 `select_threshold()`가 비용차감
기대수익 최대화로 유도한 값이므로 **거래를 내려고 낮추지 않는다**(R18).

> **시간대 결함 하나가 이 수치를 왜곡하고 있었다** (2026-08-16 P0-2). 이 저장소에는 같은
> 봉을 다른 tzinfo로 돌려주는 로더가 둘이다 — `ParquetArchiver`(KST) vs
> `ParquetBarReplaySource`(UTC). `_minutes_since_session_open()`이 인자 이름
> (`bar_open_kst`)에 기대어 `.hour`를 그대로 읽어 **재생 경로에서 540분 어긋났다**:
> 학습이 본 범위(−15~390)와 재생 추론이 본 범위(−540~−150)가 **겹치지도 않았다.**
> 값이 NaN이 아니라 그럴듯한 숫자라 흔적이 없었다(계명 6).
> **생산 경로는 무사하다**(`bar_composer.py:171`이 `.astimezone(KST)` 명시, 학습도 KST).
> 오염된 것은 `run_replay`·`run_backtest_harness`·`run_full_path_smoke` 계열 —
> 즉 **계명 2가 요구하는 바로 그 검증 경로**다. 수정 후 통과확률 최대 0.2017 → 0.6576.
> **아직 안 고친 것**: 두 로더의 시간대 불일치 자체는 그대로다(함수 하나만 고쳤다).

## 2.8 Aggregator → 통합 점수 S

```
S = Σ_h [ w(regime,h) × (P_h(+1) − P_h(−1)) × meta_h × (1 − u_h) × f_h ]
```

| Regime | 1m | 3m | 5m | 10m | 15m | 30m |
|---|---|---|---|---|---|---|
| TREND_UP / TREND_DOWN | 0.5 | 0.8 | 1.0 | 1.2 | 1.2 | **1.5** |
| RANGE | **1.2** | 1.0 | 1.0 | 0.8 | 0.6 | 0.4 |
| HIGH_VOL | 0.8 | 0.8 | 1.0 | 0.8 | 0.8 | 0.8 |
| EVENT | 0.3 | 0.3 | 0.5 | 0.5 | 0.5 | 0.5 |
| UNKNOWN | 0.5 | 0.5 | 0.5 | 0.5 | 0.5 | 0.5 |

**이 표가 이제 의미를 갖는다.** 08-06판은 "항상 UNKNOWN이라 무의미"라고 적었으나, Regime AI
결선 + 웜스타트 이후 실제 분포가 나온다 — 2026-08-16 리허설(08-14 재생) 15사이클
`{HIGH_VOL 5, RANGE 2, TREND_DOWN 8}`.

> **주의 — 반증된 손쉬운 설명 하나**: `REGIME_WEIGHTS[UNKNOWN]`은 **비어 있지 않다**
> (전 Horizon 0.5). "UNKNOWN이라 가중치가 0이라서 n_experts=0"은 틀린 설명이다.

| 인자 | 의미 | 진입을 죽이는 경우 |
|---|---|---|
| `w(regime,h)` | 위 표 | EVENT면 0.3~0.5로 축소 |
| `meta_h` | MetaLabeler 통과 여부 (0/1) | **0이면 그 전문가는 완전 제외** ← 현재 여기 |
| `1 − u_h` | `clip(ens_std / 0.5, 0, 1)` 페널티 | 앙상블이 흔들리면 발언권 소멸 |
| `f_h` | 신선도 — 확정 직후 1.0, 한 Horizon 길이 경과 시 0.0 선형 감쇠 | 의견이 늙으면 0 |

**신선도의 비대칭**: M1은 60초마다 갱신되지만 M30은 30분간 늙는다.

### `n_experts = 0`의 여섯 갈래 (2026-08-14 F-5 신설)

기여 전문가가 0명이면 `score=0.0, uncertainty=1.0`(최대 보수)로 발행하는데, **그 0에
이르는 길이 여섯이다**:

```
① views 비었음              전문가가 아예 안 붙었다(번들 미결선)
② outside_weight_table      그 Horizon이 이 국면의 가중치표에 없다
③ zero_regime_weight        표에 있으나 가중치가 0
④ blocked_by_meta           Meta-Labeler가 거부            ← 2026-08-16 실측 15/15
⑤ blocked_by_uncertainty    ens_std ≥ uncertainty_scale
⑥ blocked_by_freshness      valid_until 경과
```

종전엔 어느 길이었는지 **로그가 한 줄도 없어** W-2가 3거래일째 미확정이었다. 30m
`nan_ratio` 84.7%를 근거로 ⑤가 유력했으나 — **웜스타트가 채워지자 `ens_std`는
0.0007~0.049로 임계 근처에도 안 갔다. 가설은 기각됐다.** 유력한 것과 확정한 것은 다르다.

**한 Horizon이 여러 갈래에 동시에 걸릴 수 있으므로 전부 기록한다.** 하나만 남기면
"먼저 검사한 것"이 원인처럼 보인다. `INFO`인 것이 설계다 — 국면 UNKNOWN인 날엔 이게 정상
동작이고 WARNING이면 30분마다 울어 잡음이 된다(승격 여부는 20거래일 분포 후, R18).

**알려진 갭**: 가중치 표는 "학습 대상"(원문)이지만 분기 Walk-Forward 재추정 파이프라인이
없어 초기값 고정. 불확실성 두 번째 겹(Conformal)은 어떤 운영 루프에도 안 붙어 있다.

## 2.9 임계 → 방향

```
|S| < 0.20   → NO_TRADE (규칙 ④)
S ≥ +0.20    → LONG,  confidence = agg_p_up
S ≤ −0.20    → SHORT, confidence = agg_p_down
```

|---|---|---|---|---|---|---|
| 1m | 66,683 | 45.7 / **2.0** / 52.2 | 0.980 | 4.90배 | 34틱 | 여지 있음 |
| 3m | 22,228 | 40.4 / **18.1** / 41.5 | 0.819 | 4.09배 | 96틱 | 여지 있음 |
| 5m | 13,330 | 31.7 / **35.6** / 32.7 | 0.644 | 3.22배 | 156틱 | 여지 있음 |
| 10m | 6,656 | 24.1 / **52.0** / 23.8 | 0.480 | 2.40배 | 271틱 | 여지 있음 |
| 15m | 4,432 | 17.7 / **64.5** / 17.8 | 0.355 | 1.78배 | 425틱 | 여지 있음 |
| **30m** | 2,207 | 10.8 / **76.3** / 12.9 | **0.237** | **1.18배** | 970틱 | **게이트 도달 불가** |

> 30m flat 76.3%는 08-06 측정치와 **정확히 같다** — 레이블 기하는 피처셋과 무관하므로
> (배리어는 가격·ATR만 본다) 바뀌지 않은 것이 맞다.

### ★ 그런데 재측정이 더 깊은 것을 드러냈다 — 비용 강등 규칙이 죽어 있다

**6개 Horizon 전부에서 비용 강등이 0건이다.** 배리어 폭이 왕복 비용의 **21배(1m) ~ 606배
(30m)**라, "비용을 못 넘는 움직임은 flat으로 강등한다"는 규칙이 **한 번도 발동한 적이
없다.** 레이블이 요구하는 이동이 실제 수익성 기준과 아무 관계가 없다는 뜻이다.

그 반대편에서 무슨 일이 벌어지고 있냐면:

```
1m   flat  2.0% 중 87.8%가 |수익| 중앙 14틱   ← 왕복 비용 1.64틱을 넘는데 0으로 뭉개짐
5m   flat 35.6% 중 98.7%가 |수익| 중앙 53틱
30m  flat 76.3% 중 99.6%가 |수익| 중앙 233틱  ← 비용의 146배를 움직였는데 "flat"
```

**즉 레이블이 방향 정보를 버리고 있다.** 30m 표본의 76.3%가 "거래할 것 없음"으로 학습되는데,
그중 99.6%는 실제로 왕복 비용의 100배 넘게 움직인 구간이다.

### 이것이 §2.6·§2.7 실측의 근본 원인이다

세 관측이 하나의 사슬이다:

```
레이블 30m flat 76.3%      (§2.10, 여기)
   ↓ 모델은 배운 대로 낸다
Expert p_flat 0.473~0.967  (§2.6 재생 실측)
   ↓ 방향 확신이 없으니 메타 피처 meta_p_primary·meta_margin이 약하다
meta_p 최대 0.658 < 0.700  (§2.7 재생 실측)  →  blocked_by_meta 15/15
```

**모델이 못 배운 게 아니라, 가르친 것이 "거의 아무것도 거래하지 말라"였다.** 그래서
Meta 임계를 낮추는 것은 증상을 건드리는 일이고, 고칠 자리는 배리어 폭
(`labeling._WIDTH_ATR_MULT`)과 비용 강등 규칙이다.

배리어 폭을 건드릴 때 반드시 `run_label_geometry.py`를 함께 돌려야 하는 이유가 이것이다 —
레이블 기하학과 하류 판단 게이트가 결합돼 있고, 한쪽만 만지면 다른 쪽이 조용히 죽는다.
도구의 마지막 줄이 그것을 그대로 말한다:

# 3. 진입 실행 경로 상세

## 3.1 판단 트리거 — FuturesAIService

`feat.{h}.{symbol}` 한 건이 도착할 때마다 해당 Horizon 전문가만 추론하고 **캐시 전체를
다시 집계**한다. 집계 기준시각 `as_of`는 wall clock이 아니라 `FeatureVector.valid_until`
(봉 도메인 시각)을 쓴다 — 재생/백테스트에서 시각 도메인이 어긋나면 신선도·R11 판정이
전부 오작동한다.

**현재는 live 번들이 30m 하나뿐이라 30m `feat`가 올 때만 판단이 난다** — 하루 15봉 중
장전 봉(08:30 시작)을 뺀 **14회**가 2026-08-14 라이브 실측(`DecisionEmitted` 14건 ·
`RegimeClassified` 14건)이다. 판단 격자가 30분이라는 뜻이므로, 점검 도구가 g2 로그의
30분 공백을 적신호로 세면 **오탐**이다(2026-08-14 F-13에서 정정).

## 3.2 Meta Decision — 5개 규칙

우선순위대로 검사하고 하나라도 걸리면 즉시 NO_TRADE. **근거(`rationale`) 없는 의도는 어떤
경로로도 반환하지 않는다** — "침묵이 아니라 판단이다".

| # | 규칙 | 임계 | 관문 이름 |
|---|---|---|---|
| ① | `sys.kill` 활성 | 무조건 NO TRADE | `kill` |
| ② | Regime = EVENT **또는 UNKNOWN** | NO TRADE | `regime` |
| ③ | 전문가 의견 분산 | > 0.25 | `dispersion` |
| ④ | 우위 부족 | \|S\| < 0.20 | `score` |
| ⑤ | 방향 확정 | S ≥ +0.20 → LONG / S ≤ −0.20 → SHORT | `pass` |

### `decision_funnel` — 코드가 자기 갈래를 직접 말한다 (2026-08-12 G-1 신설)

관문 이름이 로그의 구조화 필드로 나가고 무결성 리포트가 이것을 세어 `decision_funnel`을
만든다. **왜 사유 문자열을 파싱하지 않나**: 2026-08-12에 다섯 갈래 중 ②에서 14/14가
접혔는데, 그날 리포트가 아는 것은 `DecisionEmitted: 14`뿐이었다 — ③·④·⑤가 **한 번도
평가되지 않았다**는 사실, 즉 Risk Engine·Sizer·OrderGateway가 통째로 미검증이라는 사실이
어디에도 안 남았다. `rationale`을 정규식으로 긁는 것은 다른 실패다 — **문구를 다듬는 순간
조용히 0이 된다.**

- `confidence` = 선택된 방향의 가중평균 확률(Isotonic 교정 완료분)
- `horizon` 필드는 **항상 None** — S가 이미 전 Horizon 통합값이라 지목이 무의미
- ⑥⑦(옵션 우선순위·상관 노출)은 Options AI 자체가 없어 **코드에 경로가 없다**

## 3.3 Net Expected Return

```
edge        = clip(2 × confidence − 1, 0, 1)
Net ER(틱)  = edge × ATR(M1, 14봉) − 왕복비용
왕복비용     = 수수료 + 세금 + 슬리피지 + 시장충격
```

⚠️ **명시적 근사다.** 시스템 어디에도 "얼마나 움직일까"(magnitude)를 예측하는 모델이 없다 —
`HorizonExpert`는 방향 확률만 낸다. ATR을 기대이동폭 대용으로 쓰는 것은 원문 공식이 아니라
이 구현의 선택이며, 크기 예측 Expert나 실측 캘리브레이션이 생기면 교체할 자리다.

ATR·시장충격 재료는 **전부 M1봉 전용** — S가 이미 여러 Horizon 통합값이라 "어느 Horizon
기준으로 비용을 잴 것인가"에 정답이 없어, 가장 촘촘하고 항상 최신인 M1을 공통 재료로 택했다.

**비용 모델 한계**: 호가 WS 미구독이라 슬리피지는 설정값 근사. 시장충격만 완성봉 volume으로
구조적으로 정확하다. 수수료·세금도 실측 아닌 placeholder.

## 3.4 Risk Engine 거부권

순수 판정 함수(사이징은 하지 않음). 검사 순서 그대로:

| 순서 | 규칙 | 임계 | 상태 |
|---|---|---|---|
| 1 | Net ER ≤ 0 | 무조건 거부 | 결선 |
| 2 | R11 데이터 단절 | > 30초 | 결선 |
| 3 | R13 거래소 서킷브레이커 | 정지 추정 or 재진입 관망 10분 | 결선 |
| 4 | R10 연속손실 | ≥ 3회 | **로직만 — 입력 없음**(§5.2-3) |
| 5 | R12 주문오류 | 5분 내 ≥ 3회 | 결선 |
| 6 | R2 일일손실 | ≥ 2% | 결선 |
| 7 | R6 오버나이트 자격 | 장마감 10분 전 이내 → 전면 거부 | 결선 |
| 8 | R4 / R3 증거금 | 마감 30분 내 25% / 평시 40% | 결선 |
| 9 | R5 포지션 수 | 예상 보유 종목수 초과 | 결선 |

> R10은 `consecutive_loss_limit=3`과 `record_trade_result()`가 **구현돼 있으나 부르는 곳이
> 없다** — 진입가·청산가를 매칭해 실현손익을 계산하는 Position Reconciler가 없기 때문이다.
> "구현됨 ≠ 결선됨"의 현재 사례.

설계와 다른 두 곳(의도된 선택):

- **R1(단일 포지션 최대손실 2%)은 여기서 거부하지 않는다.** Risk 통과 *후*에 Sizer가 수량을
  정하므로 검사 시점에 수량이 없다 — 대신 Sizer의 상한으로 **위반이 발생할 수 없게** 만든다.
  게이트보다 강한 보장.
- **R3·R5는 "현재 상태" 기준**이다. "이 주문을 더하면"이 아니라 "지금 이미 넘었는지"만
  본다 — 사이징 전 수량을 가정하면 Sizer와 순환 의존이 생긴다.

`minutes_to_close`가 `None`(재생/스모크 등 KRX 세션 개념이 없는 경로)이면 R4/R6는 조용히
건너뛴다. **"모른다"를 "오버나이트 아님"으로 낙관 해석하지 않는다.**

R7(순델타)·R8(순베가)·R9(매도옵션 손실)는 구현돼 있으나 옵션 실행 경로가 없어
`BrokerPosition.greeks`를 채우는 어댑터가 없다 — 게이트만 준비된 상태.

## 3.5 Position Sizer

```
risk_pct              = min(vol_target 2%, R1 2%)          ← R1을 여기서 상한으로 강제
risk_budget_krw       = equity × risk_pct
loss_per_contract_krw = ATR틱 × tick_size × point_value(50,000원)
vol_target_qty        = risk_budget_krw / loss_per_contract_krw
edge                  = clip(2 × confidence − 1, 0, 1)
qty                   = floor( vol_target_qty × edge × 0.25 × (1 − uncertainty) )
```

`qty < 1`이면 `SizerZeroQty` 로그만 남기고 주문을 만들지 않는다 — Risk 승인 후에도 0계약은
**정상 동작**이다.

**알려진 갭 2건**:
- `edge = 2p−1`은 대칭 페이오프(b=1) 가정. 정식 Kelly `f*=(p·b−q)/b`를 쓰려면 실현 거래
  통계가 필요한데 트랙레코드가 없다.
- `point_value_krw = 50,000`은 공개 정보 기반 placeholder다 — KIS API 계약승수 필드를
  실측한 값이 아니다(`symbol_master.py`가 아직 이 필드를 안 읽음).

## 3.6 Order Gateway

```
submit(req):
    1) pending 원자 등록  (전송 전!)
    2) broker.submit()
    3) 실패 시 pending 롤백 → None 반환 → 호출자가 record_order_error()(R12)
on_fill(fill):
    매칭 성공 → 정상 체결
    매칭 실패 → FillUnmatched CRITICAL + 즉시 halt (유령 포지션을 만들지 않는다)
```

주문 전송 함수는 **이것 하나뿐**이며 우회 경로 신설이 금지돼 있다(계명 1 / L1) — 미륵 최대
단일 손실(유령 포지션 −675만원)의 근본 원인이 "pending 선등록 없는 전송"이 여러 청산 경로에
흩어져 재발한 것이었다.

`halted` 상태에서도 `kind=EMERGENCY`는 통과한다 — 안 그러면 Kill Switch가 스스로 청산을
못 하는 모순이 생긴다.

**`sys.resume` (2026-08-11 신설)**: 정지 해제가 프로세스 재시작을 요구하던 것을 신호로
바꿨다. **판단한 뒤 연다** — 무조건 여는 것이 아니라 해제 조건을 확인하고 연다.
`verify_kill_switch.py`가 버튼→청산→reset→resume 전 구간을 실동작으로 채점한다.
