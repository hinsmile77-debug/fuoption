## 0. 요약 — 세 줄

1. 진입 경로는 L1(수집) → L2(피처) → L3(전문가·집계·판단) → L4(리스크·사이징) → L5(주문)까지
   **전 구간이 배선 완료**되어 있고, 관문은 7단계다.
2. 그러나 **입구가 비어 있다** — `ModelRegistry`에 `live` 번들이 0개라 `intel.futures`가
   아예 발행되지 않고, Regime AI도 미학습이라 국면이 항상 `UNKNOWN`이다.
   두 사유 각각만으로도 시스템은 **구조적으로 NO_TRADE**다.
3. 따라서 현재 손익 지표(승률·Sharpe·MDD)는 성적이 아니라 **자리표시자**다
   (`models/wiring_completeness.py`가 이 판정을 담당).

**§2를 추가하며 드러난 네 번째 사실**: 방향 결정에 실제로 쓰이는 원시 데이터는
**미니선물 체결틱 하나뿐**이고, 6개 Horizon Expert는 **전부 동일한 121개 피처 벡터**를 받는다
(Ver 1.5가 정의한 Horizon별 피처 배정은 코드에 존재하지 않는다).

## 1. 전체 경로

```
[L1] KIS WS 틱 ──> TickCollector ──> BarComposer ──> bar.{h}.{symbol}
                                                         │
[L2]                                    FeatureEngine ───┴──> feat.{h}.{symbol}
                                                         │
[L3]  FuturesAIService ──────────────────────────────────┘
        ├ HorizonExpert.predict()      (LightGBM ×5 앙상블 → p_up/p_flat/p_down, ens_std)
        ├ MetaLabeler.passes()         (meta_passed 덮어쓰기 = "지금이 배팅할 때인가")
        └ Aggregator.compute()         (Regime 가중 통합 → S) ──> intel.futures
                                                         │
[L3.5] TradingPipeline.handle_futures_view() ────────────┘
        ├ ① CircuitBreakerMonitor.observe()   (정지/해제 판정, sys.circuit_breaker 발행)
        ├ ② KillSwitch.evaluate()             (발동 시 halt + 전량 EMERGENCY 청산)
        ├ ③ MetaDecisionEngine.decide()  ──> decision.intent  (NO_TRADE도 항상 발행)
        ├ ④ 정규장(09:00~15:35) 게이트
        ├ ⑤ CostModel + ATR → Net Expected Return
[L4]    ├ ⑥ RiskEngine.evaluate()             (거부권 — 항소 불가)
        └ ⑦ PositionSizer.size()              (VolTarget × 1/4 Kelly × (1−u))
                                                         │
[L5]  OrderGateway.submit() ─────────────────────────────┘   ← 시스템 유일의 주문 경로
        pending 원자 등록 → broker.submit() → 실패 시 롤백
```

- 프로세스 간 통신은 **전부 Redis Bus**(직접 함수 호출 금지, SYSTEM.md §4-2)
- 실제 배선처: `scripts/run_g2_paper_trading.py`
- 이 프로세스는 **자체 WS 연결을 열지 않는다** — `scripts/run_l1_daily.py`가 발행하는
  `bar.*`/`feat.*`에 구독자로만 붙는다. 근거: 같은 계좌로 WS 2개를 열면 서로 반복 단절
  (2026-07-23 실측, capability_matrix.md). 대가는 L1 발행자가 살아 있지 않으면 이 경로가
  아무 신호도 못 받는다는 것.

## 2.4 호라이즌별 피처 배정 — 설계와 구현이 다른 지점

### 설계 (Ver 1.5 §3)

```
1m  : MS 65% + PX 15% + VL 10% + EV 10%                              (~55개)
3m  : MS 45% + PX 25% + VL 15% + FL  5% + EV 10%                     (~60개)
5m  : MS 25% + PX 35% + VL 15% + FL 10% + OP  5% + EV 10%            (~70개, 기준 전문가)
10m : MS 10% + PX 35% + VL 15% + FL 20% + OP  5% + RG  5% + EV 10%   (~65개)
15m : MS  5% + PX 20% + VL 15% + FL 30% + OP 10% + RG 10% + EV 10%   (~60개)
30m :          PX 15% + VL 15% + FL 20% + OP 20% + RG 20% + EV 10%   (~65개)
```

그리고 Horizon마다 **독립적으로** 4단계 깔때기(① IC 스크리닝 → ② 중복 제거 → ③ 안정성 →
④ 실효 세트 20~50개)를 통과시키게 되어 있다.

### 구현 (현재)

> **호라이즌별 배정이 코드에 없다. 6개 Horizon 전부가 완전히 동일한 121개 벡터를 받는다.**

`FeatureEngine`은 `feature_set` **하나**를 받아 모든 Horizon에 같은 계산기 목록을 돌린다.
Horizon별로 다른 `feature_set`을 주는 배선 자체가 존재하지 않는다.

배정표가 지금 구현 불가인 이유는 단순하다 — **배정의 주력 재료가 없다.** 1m의 65%(MS),
30m의 40%(OP+RG)가 통째로 부재라 배정표대로 자르면 1m은 남는 게 30%뿐이다.

### 그럼 Horizon 간 차이는 어디서 오나 — 두 곳

**① 윈도우 단위가 "해당 Horizon의 봉 수"다** (Ver 1.5 §1.3이 실제로 이걸 정당화한다):

| 피처 | M1 | M5 | M30 |
|---|---|---|---|
| `px_mom_20` | 20분 모멘텀 | 100분 | **10시간** |
| `px_mom_60` | 60분 | 5시간 | **30시간** |
| `px_hurst_120` | 2시간 | 10시간 | **60시간(≈5거래일)** |

같은 이름이지만 사실상 다른 피처이며 교차 오염이 없다.

**② 레이블이 다르다** — 배리어 폭이 0.5 → 2.0 ATR로 커지고, Horizon별로 완전히 별개의
모델이 학습된다.

### 이 차이를 정확히 부르기

구조가 원리상 틀린 것은 아니다. 다만 **"6개 전문가"가 지금은 "같은 재료를 6개 시간
해상도로 본 6개 모델"**이라는 뜻이지, 설계가 말하는 "재료가 다른 6명의 전문가"가 아니다.

실질적 부작용 하나: **1m Expert가 설계상 가장 취약하다.** 설계는 1m에서 FL·OP·RG를
"분 단위로는 갱신조차 안 되는 저속 데이터 — 1분 전문가에게는 상수나 다름없어 노이즈 학습만
유발"이라며 명시적으로 **배제**하는데, 현재 구현에서 FL을 켜면 1m도 그걸 받는다(하루 종일
같은 값 9개).

## 2.5 완성봉 → FeatureVector

`src/messiah/features/engine.py`

`bar.{h}.{symbol}` **완성봉**을 받은 시점에만 계산·발행한다(완성봉 규율 Ver 1.2 §2.2,
유예 500ms). 히스토리 상한 `_MAX_HISTORY = 200`봉.

계산 불가(워밍업 미달·표본 부족)는 **`None`으로 마킹**하고 0으로 채우지 않는다 — 0으로
채우면 "평균과 같다"는 없는 사실을 주장하게 된다. `nan_ratio`가 벡터에 함께 실려 나가고
임계 초과 시 신호 정지를 권고한다.

**두 번의 사고가 이 규율을 만들었다**:

- `deque` 슬라이스 미지원으로 계산기 대다수가 `TypeError`를 던지고 `_safe_call`이 조용히
  None으로 삼켜, 80봉 워밍업 후에도 **82개 중 72개가 항상 NaN**이었다(2026-07-26 수정).
- `px_ema_cross_60`(180봉 필요)·`px_macd_h_60`(139봉)이 당시 히스토리 상한 130을 넘어
  **프로덕션에서 항상 NaN인 채로 학습**되고 있었는데, 매일 찍히는 `nan_ratio=0.0165`(=2/121)가
  "정상 수준"으로 읽혔다(2026-08-04 발견 → 상한 200으로).

## 2.6 Expert → 방향 확률

`src/messiah/strategy/futures/expert.py`

```
FeatureVector.values (dict, None=NaN)
   ↓ feature_row()  — 학습 시점과 동일한 정렬 순서로 행 조립
   │                  (train()과 predict()가 공유하는 유일한 경로 — 계명 6)
   ↓ LightGBM ×5   (seed만 다른 동일 하이퍼파라미터, Ver 1.6 §2.3 미니 앙상블)
member_probs [5 × 3]
   ↓ ens_std = P(+1) 5개의 표준편차              ← 불확실성 원료(Ver 1.2 §6)
   ↓ mean(axis=0) → ProbabilityCalibrator(Isotonic, 선택적)
p_down / p_flat / p_up  +  top_features(gain 상위 5)  +  valid_until
```

- LightGBM은 NaN을 네이티브로 처리한다(결측 자체가 분기 정보)
- 클래스 매핑 `{-1:0, 0:1, +1:2}`는 모듈 상수로 고정 — 순서를 바꾸면 저장된 모델과 어긋난다(L25)
- `meta_passed`는 여기서 **항상 True**다. 실제 판정은 §2.7
- `feature_set` 불일치는 `FeatureSetMismatchError`로 즉시 중단 — 침묵한 채 엉뚱한 순서의
  벡터를 만들지 않는다

## 2.7 MetaLabeler → "지금이 배팅할 때인가"

`src/messiah/strategy/futures/meta_labeler.py`

1차 모델은 "어느 쪽인가"에 강하고 "지금이 때인가"에 약하다(Ver 1.2 §5.1) — 역할을 분리해
**승률 필터를 독립적으로 학습**한다. 얕은 LightGBM(depth 3~4, num_leaves ≤ 15) —
"필터는 단순해야 필터답다".

메타 피처는 설계상 8종(1차 확률·마진·앙상블 분산·Regime·실현변동성·스프레드·이벤트
근접도·시간대)이지만 **지금 낼 수 있는 5개**만 쓴다 — Regime(미학습)·스프레드(호가
미구독)·이벤트 근접도는 부재.

- **임계값 선택**: 정확도 최대화가 아니라 **비용 차감 후 기대수익 최대화** 그리드서치
- **Look-ahead 방지**: `PurgedKFold` out-of-fold 예측을 입력으로 씀(구조적 강제)
- 결과가 `meta_passed`를 덮어쓰고, **False면 그 전문가는 집계에서 완전히 제외**된다(가중치 ×0)
- **MetaLabeler가 없는 Horizon은 필터링 없이 통과**한다 — 배관을 끊지 않기 위한 선택이지만
  프로덕션 원칙은 전 Horizon에 붙이는 것이다(Ver 1.2 §5.2)

## 2.8 Aggregator → 통합 점수 S

`src/messiah/strategy/futures/aggregator.py`

```
S = Σ_h [ w(regime,h) × (P_h(+1) − P_h(−1)) × meta_h × (1 − u_h) × f_h ]
```

Regime 가중치 표 (Ver 1.2 §7.1 원문 그대로 상수):

| Regime | 1m | 3m | 5m | 10m | 15m | 30m |
|---|---|---|---|---|---|---|
| TREND_UP / TREND_DOWN | 0.5 | 0.8 | 1.0 | 1.2 | 1.2 | **1.5** |
| RANGE | **1.2** | 1.0 | 1.0 | 0.8 | 0.6 | 0.4 |
| HIGH_VOL | 0.8 | 0.8 | 1.0 | 0.8 | 0.8 | 0.8 |
| EVENT | 0.3 | 0.3 | 0.5 | 0.5 | 0.5 | 0.5 |
| **UNKNOWN** | 0.5 | 0.5 | 0.5 | 0.5 | 0.5 | 0.5 |

논리는 명확하다 — 추세장에선 긴 Horizon에, 횡보장에선 짧은 Horizon에 무게를 싣는다.
**현재는 Regime AI 미학습이라 항상 UNKNOWN(전부 0.5)** 이며, 어차피 Meta Decision 규칙 ②가
UNKNOWN을 NO TRADE로 처리하므로 실질적으로 무의미하다.

| 인자 | 의미 | 진입을 죽이는 경우 |
|---|---|---|
| `w(regime,h)` | 위 표 | EVENT면 0.3~0.5로 축소 |
| `meta_h` | MetaLabeler 통과 여부 (0/1) | **0이면 그 전문가는 완전 제외** |
| `1 − u_h` | `clip(ens_std / 0.5, 0, 1)` 페널티 | 앙상블이 흔들리면 발언권 소멸 |
| `f_h` | 신선도 — 확정 직후 1.0, 한 Horizon 길이 경과 시 0.0 선형 감쇠 | 의견이 늙으면 0 |

**신선도의 비대칭**: M1은 60초마다 갱신되지만 M30은 30분간 늙는다 — M30 의견은 발행 직후에만
온전한 무게를 갖고, 그 뒤로는 선형으로 발언권을 잃는다.

부산물: `agg_p_up`/`agg_p_down`(가중평균 확률), `uncertainty`(가중평균 u_h),
`dispersion`(기여 Horizon들의 방향점수 표준편차 → 규칙 ③ 입력), `top_features`(XAI 상위 5개,
`{horizon}:{feature}` 형태라 어느 전문가의 근거인지 남는다).

기여 전문가가 0명이면 `score=0.0, uncertainty=1.0`(최대 보수)로 발행한다.

**알려진 갭**: 가중치 표는 "학습 대상"(원문)이지만 분기 Walk-Forward 재추정 파이프라인이
없어 초기값 고정. 불확실성 두 번째 겹(Conformal)은 어떤 운영 루프에도 안 붙어 있어 앙상블
분산만 쓴다.

## 2.9 임계 → 방향

```
|S| < 0.20   → NO_TRADE (규칙 ④)
S ≥ +0.20    → LONG,  confidence = agg_p_up
S ≤ −0.20    → SHORT, confidence = agg_p_down
```

전체 규칙 우선순위는 §3.3.

## 2.10 반드시 알아야 할 구조적 결합 — flat 비율이 방향 결정의 천장을 정한다

**교정된 모델의 `|S|`는 `1 − flat_share`를 넘을 수 없다.**

30m은 flat 76.3%라 **천장이 0.237** — 진입 게이트(0.20) 바로 위다. 즉 30m Expert는 완벽하게
맞혀도 임계를 겨우 넘는다.

배리어 폭(`_WIDTH_ATR_MULT`)을 건드릴 때 반드시 `models/label_geometry.py`를 함께 돌려야
하는 이유가 이것이다 — 레이블 기하학과 하류 판단 게이트가 결합돼 있고, 한쪽만 만지면 다른
쪽이 조용히 죽는다.

| 항목 | 설계 | 현재 |
|---|---|---|

## 3.1 판단 트리거 — FuturesAIService

`src/messiah/strategy/futures/service.py`

`feat.{h}.{symbol}` 한 건이 도착할 때마다 해당 Horizon 전문가만 추론하고, **캐시 전체를

## 3.2 Meta Decision — 5개 규칙

`src/messiah/strategy/decision/meta_decision.py`

우선순위대로 검사하고 하나라도 걸리면 즉시 NO_TRADE. **근거(`rationale`) 없는 의도는 어떤
경로로도 반환하지 않는다** — "침묵이 아니라 판단이다"(Ver 2.0 §3.2).

| # | 규칙 | 임계 |
|---|---|---|
| ① | `sys.kill` 활성 | 무조건 NO TRADE |
| ② | Regime = EVENT **또는 UNKNOWN** | NO TRADE |
| ③ | 전문가 의견 분산 | > 0.25 |
| ④ | 우위 부족 | \|S\| < 0.20 |
| ⑤ | 방향 확정 | S ≥ +0.20 → LONG / S ≤ −0.20 → SHORT |

- `confidence` = 선택된 방향의 가중평균 확률(Expert 단계에서 Isotonic 교정 완료분)
- `horizon` 필드는 **항상 None** — S가 이미 전 Horizon 통합값이라 지목이 무의미
- ⑥⑦(옵션 우선순위·상관 노출)은 Options AI 자체가 없어 **코드에 경로가 없다**

## 3.3 Net Expected Return

`src/messiah/strategy/pipeline.py` · `src/messiah/risk/cost_model.py`

```
edge        = clip(2 × confidence − 1, 0, 1)
Net ER(틱)  = edge × ATR(M1, 14봉) − 왕복비용
왕복비용     = 수수료 + 세금 + 슬리피지 + 시장충격
```

⚠️ **명시적 근사다.** 시스템 어디에도 "얼마나 움직일까"(magnitude)를 예측하는 모델이 없다 —
`HorizonExpert`는 방향 확률만 낸다. ATR을 기대이동폭 대용으로 쓰는 것은 원문 공식이 아니라
이 구현의 선택이며, 크기 예측 Expert나 실측 캘리브레이션이 생기면 교체할 자리다.

ATR·시장충격 재료는 **전부 M1봉 전용** — S가 이미 여러 Horizon 통합값이라 "어느 Horizon
기준으로 비용을 잴 것인가"에 정답이 없어, 가장 촘촘하고 항상 최신인 M1을 공통 재료로 택했다.

**비용 모델 한계**: 호가 WS를 구독하지 않아 슬리피지는 설정값 근사다. 시장충격만 완성봉
volume으로 구조적으로 정확하다.

## 3.4 Risk Engine 거부권

`src/messiah/risk/risk_engine.py` · 순수 판정 함수(사이징은 하지 않음)

검사 순서 그대로:

| 순서 | 규칙 | 임계 | 상태 |
|---|---|---|---|
| 1 | Net ER ≤ 0 | 무조건 거부 (Ver 1.1 §4-2) | 결선 |
| 2 | R11 데이터 단절 | > 30초 | 결선 |
| 3 | R13 거래소 서킷브레이커 | 정지 추정 or 재진입 관망 10분 | 결선 |
| 4 | R10 연속손실 | ≥ 3회 | **미결선**(§4.2) |
| 5 | R12 주문오류 | 5분 내 ≥ 3회 | 결선 |
| 6 | R2 일일손실 | ≥ 2% | 결선 |
| 7 | R6 오버나이트 자격 | 장마감 10분 전 이내 → 전면 거부 | 결선 |
| 8 | R4 / R3 증거금 | 마감 30분 내 25% / 평시 40% | 결선 |
| 9 | R5 포지션 수 | 예상 보유 종목수 초과 | 결선 |

설계와 다른 두 곳(의도된 선택):

- **R1(단일 포지션 최대손실 2%)은 여기서 거부하지 않는다.** Risk 통과 *후*에 Sizer가 수량을
  정하므로 검사 시점에 수량이 아직 없다 — 대신 Sizer의 사이징 상한으로 **위반이 발생할 수
  없게** 만든다. 게이트보다 강한 보장.
- **R3·R5는 "현재 상태" 기준**이다. "이 주문을 더하면 얼마가 될지"가 아니라 "지금 이미
  넘었는지"만 본다 — 사이징 전 수량을 가정하면 Sizer와 순환 의존이 생긴다.

`minutes_to_close`가 `None`(재생/스모크 등 KRX 세션 개념이 없는 경로)이면 R4/R6는 조용히
건너뛴다. "모른다"를 "오버나이트 아님"으로 낙관 해석하지 않는다.

R7(순델타)·R8(순베가)·R9(매도옵션 손실)는 별도 메서드로 구현돼 있으나, 옵션 주문 실행 경로
자체가 없어 `BrokerPosition.greeks`를 채우는 어댑터가 없다 — 게이트만 준비된 상태.

## 3.5 Position Sizer

`src/messiah/risk/sizer.py`

```
risk_pct              = min(vol_target 2%, R1 2%)          ← R1을 여기서 상한으로 강제
risk_budget_krw       = equity × risk_pct
loss_per_contract_krw = ATR틱 × tick_size × point_value(50,000원)
vol_target_qty        = risk_budget_krw / loss_per_contract_krw
edge                  = clip(2 × confidence − 1, 0, 1)
qty                   = floor( vol_target_qty × edge × 0.25 × (1 − uncertainty) )
```

`qty < 1`이면 `SizerZeroQty` 로그만 남기고 주문을 만들지 않는다 — Risk 승인 후에도 0계약은
**정상 동작**이다.

**알려진 갭 2건**:
- `edge = 2p−1`은 대칭 페이오프(b=1) 가정. 정식 Kelly `f*=(p·b−q)/b`를 쓰려면 실현 거래
  통계가 필요한데 트랙레코드가 없다. Self Evaluation(Phase 5)이 쌓이면 교체할 자리.
- `point_value_krw = 50,000`은 공개 정보 기반 placeholder다 — KIS API 계약승수 필드를 직접
  실측한 값이 아니다(`symbol_master.py`가 아직 이 필드를 안 읽음).

## 3.6 Order Gateway

`src/messiah/execution/order_gateway.py`

```
submit(req):
    1) pending 원자 등록  (전송 전!)
    2) broker.submit()
    3) 실패 시 pending 롤백 → None 반환 → 호출자가 record_order_error()(R12)
on_fill(fill):
    매칭 성공 → 정상 체결
    매칭 실패 → FillUnmatched CRITICAL + 즉시 halt (유령 포지션을 만들지 않는다)
```

주문 전송 함수는 **이것 하나뿐**이며 우회 경로 신설이 금지돼 있다(계명 1 / L1) — 미륵 최대
단일 손실(유령 포지션 −675만원)의 근본 원인이 "pending 선등록 없는 전송"이 여러 청산 경로에
흩어져 재발한 것이었다.

`halted` 상태에서도 `kind=EMERGENCY`는 통과한다 — 안 그러면 Kill Switch가 스스로 청산을
못 하는 모순이 생긴다.

# 4. 진입을 막는 관문 — 전체 목록

`TradingPipeline.handle_futures_view()` 실행 순서 그대로:

| # | 위치 | 조건 | 로그 태그 |
|---|---|---|---|
| 0 | Aggregator | meta_passed=0 / 신선도 0 / 전문가 0명 → S≈0 | — |
| 1 | CircuitBreaker | CONFIRMED → `gateway.halt()` (청산은 안 함 — 정지 중엔 주문이 거부됨) | `CircuitBreakerConfirmed` |
| 2 | KillSwitch | 일일손실 2% · 데이터단절 지속 30초 → **halt + 전량 EMERGENCY 청산** | `KillSwitch` |
| 3 | MetaDecision ①~④ | kill · EVENT/UNKNOWN · 분산>0.25 · \|S\|<0.20 | `DecisionEmitted` |
| 4 | 세션 게이트 | 09:00~15:35 밖 → **판단은 다 하고 주문만 생략** | `OutOfSessionNoTrade` |
| 5 | ATR 워밍업 | ATR 없음/0 → 조용히 대기 | — |
| 6 | RiskEngine | §3.4의 9개 | `RiskReject` |
| 7 | Sizer | qty = 0 | `SizerZeroQty` |
| 8 | Gateway | halted / 브로커 거부 | `OrderSubmit` |

**차단 계층은 Meta-Labeler / Risk / KillSwitch 3개 고정**(R18) — CB는 그 위에 얹힌 R13
입력이지 4번째 차단 계층이 아니다.

### 설계 의도가 드러나는 지점 두 곳

- **세션 게이트는 `decision.intent` 발행 *뒤*에 둔다.** 08:45~09:00 장전 구간에도 판단은
  평소와 똑같이 수행하고 그 결과도 그대로 발행하되 주문 제출만 건너뛴다 — 그래야 "장전에
  시스템이 무엇을 하려 했는가"가 화면·로그에 남아 개장 직후 동작을 예측·검증할 수 있다.
  (틱은 실측으로 08:45:00부터 들어오며, 그 데이터는 수집·아카이브·웜업에 그대로 쓴다.)
- **CB 해제는 사람 확인 없이 자동 복구**, KillSwitch는 사람 확인 필수. CB는 알려진·시장
  전체·일시적 이벤트라 자동 복구가 합당하다는 판단이다. 충돌 회피를 위해 CB가 WARNING
  이상이면 KillSwitch에는 `data_age_seconds=0.0`을 넘겨 R11이 중복 발동하지 못하게 한다.

# 5. 현재 개발 상태

## 5.1 결선 완료

| 구간 | 상태 |
|---|---|
| L1 수집 → 봉 합성 → 아카이브 | 운영 중 (`run_l1_daily.py`, 평일 08:35 스케줄러) |
| L1 옵션체인·수급 폴링 | 운영 중 (수집·아카이브만 — 소비 피처 없음) |
| L2 FeatureEngine + feature_set 스펙 | 결선 (2026-08-04 F0-1) |
| L2 피처 품질 관문 (`features/gate.py`) | 신설 (2026-08-04 F0-3) — 판정만, 자동 격리 없음 |
| L3 Expert → MetaLabeler → Aggregator | 결선 |
| L3.5 Meta Decision | 결선 (①~⑤) |
| L4 CostModel · RiskEngine · Sizer | 결선 (R10 제외) |
| L5 OrderGateway · SimBroker | 결선 |
| 안전장치 KillSwitch · CircuitBreakerMonitor | 결선 (벽시계 워치독 포함) |
| Phase 5 Registry · Shadow · Self-Eval | 인프라 완료 |

## 5.2 진입이 실제로 나지 않는 이유 (우선순위 순)

1. **`ModelRegistry`에 `live` 번들 0개**
   `_load_futures_service()`가 Horizon별 `registry.get_live(h)`를 조회해 없으면 건너뛴다 →
   `FuturesAIService`가 전문가 0개로 기동 → `intel.futures` **미발행** →
   `handle_futures_view()`가 하루 종일 한 번도 안 불림.
   **파급 사고 실측**: 2026-07-31, 이 상태 때문에 CB 해제 코드가 있던 유일한 경로가 죽어
   워치독이 08:53에 건 정지가 15:35까지 **6시간 42분** 안 풀렸다. → `_apply_circuit_breaker_event()`
   단일 경로 + 워치독 해제 처리로 수정 완료.

2. **Regime AI 미학습** — 실측 데이터 부족으로 학습된 `RegimeAI` 인스턴스가 없다.
   `RegimeState`를 한 번도 못 받으면 국면이 `UNKNOWN`으로 유지되고, Meta Decision 규칙 ②가
   무조건 NO TRADE를 낸다. **안전한 기본 동작이지만**, 전문가 번들이 붙어도 이것만으로
   거래가 안 난다.

3. **Position Reconciler 부재** → R10(연속손실) 미결선, 거래별 실현손익 매칭 불가.
   G2 일일수익률은 `SimBroker.account().total_equity` 변화율 근사로 대체 중.

4. **정보 폭 부족(§2.11)** — MS/OP/RG 카테고리 전무, 호라이즌별 배정 미구현. 위 1~3이
   풀려도 **판단 재료 자체가 설계의 1/3**이라는 사실은 남는다.

## 5.3 계측 장치

`decisions_emitted`(NO_TRADE 포함) / `accepted_orders` 두 카운터가
`models/wiring_completeness.py`의 입력이다. **이 값이 0이면 승률·Sharpe·MDD는 성적이 아니라
자리표시자**로 표시된다 — 2026-08-03에 `decisions_emitted=0`이라는 사실 자체가 "번들이
하나도 안 붙었다"는 진단의 근거였다.

# 6. 진입을 여는 데 필요한 순서

앞의 둘이 없으면 이 흐름 전체가 구조적으로 NO_TRADE이므로 순서가 정해져 있다.

1. **Horizon별 `live` 번들 승격** — 실데이터 학습 → G1 백테스트 관문 통과 → Registry 승격.
   이것이 없으면 `intel.futures`가 아예 안 나므로 아래 모든 것이 무의미하다.
2. **Regime AI 결선** — UNKNOWN이 풀려야 Meta Decision ②를 통과한다. Aggregator의 Regime
   가중치 표(§2.8)도 이때부터 비로소 의미를 갖는다.
3. **Position Reconciler** — R10 결선 + 실현손익 매칭 → Self Evaluation·Kelly `edge` 근사
   교체·Cost Model 자기보정의 공통 전제.

정보 폭 확장은 별도 축이며 소급 가능성 순으로 잡혀 있다:

| 순위 | 항목 | 소급 가능? | 비고 |
|---|---|---|---|
| F1 | **EV 결선**(`v2026.08-ev`) | **가능** | 시각 함수라 163거래일에 바로 붙음 |
| F2 | **FL A/B**(`v2026.08-fl`) | 부분 | 현물 일별 수급만, 파생 장중은 2026-08-05부터 누적 |
| F3 | OP 카테고리 | 불가 | 체인은 수집 중 — 계산기만 만들면 되나 이력이 짧음 |
| F4 | MS 카테고리 | 불가 | 호가 WS 구독부터 |
| F5 | RG 카테고리 | 불가 | 데이터소스 미착수 |
| — | Horizon별 배정 | — | MS/OP/RG가 생긴 뒤에야 의미 있음 |

그 외 "알려진 갭": 크기 예측 Expert(Net ER의 ATR 근사 교체), 계약승수 실측
(`point_value_krw`), 가중치 표 Walk-Forward 재추정, Conformal 운영 루프 결선.
