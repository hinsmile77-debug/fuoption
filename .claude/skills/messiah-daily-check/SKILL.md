# MESSIAH 일일 운영 점검

## 이 스킬이 하는 일

한 문장으로: **"오늘 메시아가 설계대로 살았는가"를 로그로 심문하고, 안 그런 부분에 대해 고칠 계획과 더 나아갈 계획을 내놓는다.**

건강검진에 비유하면 — §1~§4가 채혈·촬영(증거 수집), §5가 판독(이상점), §6이 처방(fix 계획), §7이 생활습관 개선(고도화). 판독 없이 수치만 나열하는 보고서는 이 스킬의 실패다.

산출은 항상 세 부분이다. 사용자가 매번 요청해 온 형식이고, 순서도 고정이다.

1. **이상점 정리보고** — 국면(장전/장중/장후)별 작업흐름 이상점
2. **Fix 작업 구현계획** — 우선순위(P0/P1/P2)와 함께
3. **고도화 방안** — 당일 작동 점검결과를 근거로

# 대원칙 — 이 둘을 어기면 나머지를 다 지켜도 실패다

## 대원칙 A. 장전·장중·장후 리포트는 알기 쉽게 쓴다

리포트는 **전문가가 아닌 사람이 읽어도 무슨 일이 있었고 무엇을 해야 하는지 알 수 있어야 한다.**

> **줄이라는 뜻이 아니다 — 쉽게 만드는 대상은 순서와 표현이지 내용이 아니다.**
> 근거·로그 인용·파일과 함수 이름·조항 번호는 **하나도 빼지 않는다.** 증거를 덜어내서 읽기 쉬워진
> 보고서는 이 스킬의 실패다. 바꾸는 것은 **무엇을 먼저 놓느냐**와 **어떻게 부르느냐** 둘뿐이다.

병원 진단서에 비유하면 — 검사 수치와 소견은 그대로 두되, 맨 앞에 "지금 위험하지 않습니다,
다음 주에 재검하세요"를 사람 말로 적는 것이다. **수치를 지우는 것이 아니다.**

### 실행 규칙 5개 (슬로건 아님 — 하나씩 통과시킨다)

**① 결론부터 — `§0`은 전문용어 없이 쓴다.**

`## 0. 오늘 한눈에`는 **약어·로그 태그명·파일경로·조항번호를 단 하나도 쓰지 않는다.**
"지금 위험한가 / 무엇이 잘못됐나 / 사람이 뭘 해야 하나" 세 가지만 평문으로 쓴다.
전문용어가 필요해지는 순간부터가 `§1`이다.

- ✗ `RegimeSeeded 0건 — F-5 미반영으로 J-5 판정 불가`
- ✓ `어제 고친 내용이 아직 프로그램에 반영되지 않았습니다. 그래서 오늘 아침 시장 상황 판단이 어제와 똑같이 "모름" 상태로 시작합니다. 거래에 직접 위험은 없습니다.`

**② 약어는 첫 등장에서 한 번 풀어쓴다.**

그 문서 안에서 **처음 나올 때 딱 한 번** 괄호로 푼다. 두 번째부터는 약어만 쓴다.
대상은 내부 코드명(F-5, J-12, R11, W24), 로그 태그, 지표명, 업계 약어 **전부**다.

- ✓ `R11(장중 배포 금지 규칙)` · `J-5(어제 세운 오늘 검증 항목 5번)` · `p90(100번 중 90번이 이 값 이하)`
- ✓ `MDD(Maximum Drawdown, 최고점 대비 최대 하락폭)` · `레그(leg, 옵션 조합에서 개별 종목 한 다리)`
- ✗ 아무 설명 없이 `FixVerificationRecurred가 4건`

**③ 숫자에는 단위와 기준을 함께 적는다.** 맨숫자는 쓰지 않는다.

| 종류 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 가격·지수 | `1047.02` | `1047.02pt(코스피200 지수 포인트)` |
| 손익 | `-320,000` | `-320,000원(자본 대비 -0.64%)` |
| 수량 | `3계약` | `3계약(선물 포지션 3개 · 옵션이면 레그 수로 표기)` |
| 낙폭 | `MDD 4.1%` | `MDD 4.1%(당일 peak 대비 · 자본 대비로는 2.2%)` |
| 지연 | `925ms` | `925ms(완성봉 유예 500ms의 1.85배)` |
| 비율 | `61.2%` | `61.2%(정상일 99% 이상 · 임계 95%)` |

**비교 기준이 없는 숫자는 정보가 아니다.** 손익률·낙폭은 **자본 대비인지 peak 대비인지**를 항상 밝히고,
둘 다 의미가 있으면 둘 다 병기한다. 수량은 **포지션(계약) 단위인지 레그 단위인지**를 밝힌다.

**④ 「영향」은 평문 한 문장으로 쓴다.**

각 이상점의 `**영향**:` 줄은 **기술용어 없이, 한 문장으로, 무엇이 어떻게 되는지**만 쓴다.
기술적 부연은 바로 아래 `**영향(기술)**:` 로 따로 단다. **두 줄로 나누되 둘 다 쓴다** — 기술 설명을 지우는 것이 아니다.

- ✓ `**영향**: 오늘 아침 첫 매매 판단이 평소보다 조심스러운 쪽으로 치우칩니다. 손해가 나는 것은 아니지만 기회를 놓칠 수 있습니다.`
- `**영향(기술)**: 09:00 첫 사이클의 regime이 UNKNOWN → 집계기 가중치표 폴백 + Meta 임계 +0.10.`

**⑤ 사용자가 할 일은 맨 끝 한 절에 모은다.**

본문 곳곳에 흩어 놓지 않는다. 마지막 `## 사용자 조치` 절에 **번호 목록**으로 집결시키고,
각 항목에 **① 지금 할 일 ② 걸리는 시간 ③ 안 하면 생기는 일** 셋을 적는다.
사람이 **이 절만 읽고 자리를 떠도** 그날 운영이 굴러가야 한다.

```markdown
## 사용자 조치

1. **UI를 브라우저로 한 번 열어 주세요** — http://localhost:8511
   - 걸리는 시간: 10초
   - 안 하면: 화면 갱신이 제대로 되는지 오늘도 확인할 수 없습니다 (D-2 판정 보류 4일째)
2. **장 마감(15:35) 뒤에 "커밋해"라고 말씀해 주세요**
   - 걸리는 시간: 제가 5분, 확인 포함 10분
   - 안 하면: 내일 아침도 어제 고친 내용 없이 시작합니다
```

## 대원칙 B. 하루에 파일 하나 — 장전이 만들고, 장중·장후가 이어 붙인다

**판정 기준 한 문장: 이 파일 하나만 읽고 그날이 전부 재구성되도록 구성한다.**

### ① 하루 한 파일 · append 전용

- 파일명은 **`logs/dailycheck/<YYYY-MM-DD>_report.md`** 하나뿐이다.
- **`_pre_report.md` / `_intra_report.md` / `_post_report.md` 같은 국면 접미사 파일은 금지.**
  세 파일로 흩어지면 그날을 알려고 세 번 읽어야 하고, 셋이 서로를 반박해도 아무도 모른다.
- **장전이 파일을 만들고(`제1부`), 장중이 이어 붙이고(`제2부`), 장후가 이어 붙여 완성한다(`제3부`).**
- 같은 국면을 하루에 두 번 점검하면 **새 파일이 아니라 같은 파일에 절을 하나 더 붙인다**
  (`제2부 장중 (12:30)` 다음에 `제2부-B 장중 재점검 (14:10)`). 2026-08-14 F-12의 "앞 보고서를
  덮지 않는다"는 요구는 이 방식으로 더 강하게 지켜진다.
- 증거 다이제스트는 국면별로 따로 둔다(`evidence_<YYYYMMDD>_<phase>.md`) — 그건 원자료지 보고서가 아니다.

> **핵심 안전장치 — 앞 국면 절의 본문을 고치거나 지우지 않는다.**
>
> 장중에 장전 판단이 틀렸음이 드러나도 **장전 절은 그대로 둔다.** 정정은 **뒤 국면 절에서** 하고,
> 앞 절에는 **한 줄 포인터만** 단다: `> ↩️ 12:30 정정 — 2-3 참조`.
>
> 그래야 **왜 그때 그렇게 판단했는가**가 남는다. 앞 절을 고쳐 버리면 보고서는 언제나 옳아 보이고,
> 판단이 어디서 어긋났는지 배울 자리가 사라진다. dev_memory를 덮어쓰지 않는 규칙과 같은 이유다.
>
> **예외는 하나** — 오탈자·깨진 링크처럼 **의미를 바꾸지 않는 수정.** 그 외 전부 뒤에서 처리한다.

### ② 이월 처리 — 앞 국면 항목을 전부 처분한 뒤 시작한다

뒤 국면은 자기 이야기를 시작하기 **전에**, 앞 국면이 남긴 **모든** 항목을 아래 다섯 중 하나로 처분한다.
빠뜨린 항목이 하나라도 있으면 그 국면 절은 완성이 아니다.

| 표시 | 뜻 | 쓰는 법 |
|---|---|---|
| ✅ **해소** | 없어졌다 | 무엇으로 확인했는지 근거 한 줄 |
| 🔄 **지속** | 그대로다 | **새 번호를 붙이지 않는다.** 원래 번호를 그대로 쓴다 |
| ⬆️ **격상** / ⬇️ **완화** | 심각도가 바뀌었다 | `P1 → P0` 처럼 적고, 바뀐 이유 |
| ↩️ **정정** | 앞 판단이 틀렸다 | 뒤 국면 절에 새 번호로 쓰고, 앞 절에 포인터 한 줄 |
| 🆕 **신규** | 이번 국면에 처음 봤다 | 다음 번호를 이어 받는다 |

각 국면 절은 **`### 이월 처리`** 표로 시작한다:

```markdown
### 이월 처리 (장전 → 장중)

| 번호 | 항목 | 처분 | 근거 |
|---|---|---|---|
| 1-1 | 어제 구현분 미커밋 | 🔄 지속 | 12:30 현재 `git diff` 동일. 장중이라 커밋 불가 |
| 1-3 | 손실원장 "장중 재기동" 오표기 | ⬆️ 격상 P1→P0 | 12:31 재기동으로 실제 소실 발생, 오표기가 규모를 가림 |
| C-4 | UI 화면 갱신 확인 | ✅ 해소 | 10:12 사용자 개방 후 해당 로그 3건 확인 |
| K-3 | 국면 시드 로그 | ↩️ 판정 → 2-1 | 장전에 "내일 판정"으로 미뤘으나 오늘 결론 남 |
```

- **이상점 번호는 하루 안에서 이어진다.** 장전 `1-1~1-5` → 장중 `1-6~1-8` → 장후 `1-9~` .
  국면마다 1번부터 다시 세지 않는다. **`1-3`은 그날 안에서 언제나 같은 것을 가리킨다.**
- **지속 항목에 새 번호를 붙이지 않는다.** 같은 결함이 번호를 세 개 갖게 되면
  "오늘 이상점 N건"이 사고 규모를 뜻하지 않게 된다 — 2026-08-19 F-4가 지표 공유를 금지한 것과 같은 이유다.
- **앞 국면이 등록한 관측 항목(K-n / J-n / "확인 필요")도 전부 닫는다** — `판정` / `보류` / `이월` 중 하나.
  보류·이월이면 **무엇을 더 보면 닫히는지**와 **언제 닫는지**를 반드시 쓴다.

### ③ 장후 = 그날의 종합 완성본

장후 절은 자기 국면만 쓰는 것이 아니라 **하루를 닫는다.** 아래 다섯이 전부 있어야 한다.

1. **종합 판정표** — 장전·장중·장후 세 줄. 각각 `정상 / 조건부 / 이상`과 근거 요약
2. **당일 이상점 통합 대장** — 그날 전 항목을 번호순 한 표로. `발견 국면 · 최종 심각도 · 최종 처분(✅🔄⬆️⬇️↩️)`
3. **종가 기준 최종 손익 · 절대원칙 판정** — 실현/평가 손익(원 · 자본 대비 %), MDD(peak 대비 · 자본 대비 병기),
   포지션 수(계약/레그 명시), 불변원칙 5개·금지 15계명 위반 유무
4. **제4부(다음 거래일 관측 예정) · 제5부(dev_memory 반영)**
5. **`## 사용자 조치`** — 대원칙 A-⑤ 형식으로, 그날 전체를 통틀어 맨 마지막에

**자체 검증**: 다 쓴 뒤 스스로 물어라 — *"이 파일만 읽은 사람이 오늘 09:00부터 15:35까지 무슨 일이
있었는지, 지금 무엇을 해야 하는지 말할 수 있는가."* 아니면 아직 덜 쓴 것이다.

## 0. 시작 전 — 국면과 날짜를 확정한다

인자로 국면이 넘어왔으면 그것을 쓴다. 없으면 KST 현재시각으로 추론하되, **추론한 값을 첫 줄에 명시**한다.

| 국면 | 인자 | 시간대(KST) | 무엇을 묻는가 | 보고서에서 |
|---|---|---|---|---|
| 장전 | `pre` | ~09:00 | 오늘 거래할 자격이 되는가 | 파일 **생성** · 제1부 |
| 장중 | `intra` | 09:00~15:35 | 지금 설계대로 돌고 있는가 | **append** · 제2부 |
| 장후 | `post` | 15:35~ | 오늘 하루가 설계대로였는가 | **append + 종합 완성** · 제3부 |

날짜는 기본 오늘. 과거일(`7/23` 등)이 지정되면 그 날로 본다.

**장중·장후는 먼저 `logs/dailycheck/<YYYY-MM-DD>_report.md`를 읽는다.** 없으면 앞 국면 점검이
돌지 않은 것이다 — 그 사실 자체를 이상점으로 적고(관측 공백), 자기 절부터 시작하되
파일은 새로 만든다. 있으면 **끝에 이어 붙인다. 앞부분은 건드리지 않는다**(대원칙 B-①).

**리포 루트 확정**: `SYSTEM.md`와 `dev_memory/`를 함께 가진 디렉터리.

  `C:\Users\82108\PycharmProjects\fuoption` 접근을 먼저 요청한다. 연결 후 bash 경로는 `mnt/fuoption`.

## 1. 증거를 먼저 모은다 (분석보다 앞선다)

로그 원본은 하루치가 130~240KB다. 그대로 읽으면 컨텍스트가 증거로 가득 차 판단할 여력이 남지 않는다. 반드시 수집기를 먼저 돌린다.

```bash
python3 scripts/collect_evidence.py --phase post --date 2026-08-11
```

- Windows/Claude Code 로컬: `python scripts/collect_evidence.py --phase post`

## 3. 설계와 대조한다 — 이 스킬의 핵심

증거를 **기준**에 대야 이상점이 된다. 기준은 네 군데다.

1. **`SYSTEM.md`** — 개발 헌법. 아키텍처 불변 원칙 5개, 코딩 규칙 R1~R18, 금지 15계명. 로그에서 본 행동이 이 중 무엇을 위반하는지 조항 번호로 지목한다.
2. **`Derivatives_AI_Master_Plan_Ver2.0.md`** 및 필요 시 하위 버전 — 로드맵 W단계, 해당 국면에 무엇이 돌아야 하는지.
3. **`dev_memory/DECISION_LOG.md` · `NEXT_TODO.md`** — 이미 알고 있는 문제인가, 새로 생긴 문제인가. **이미 결정된 사안을 새 발견인 양 보고하지 않는다.** 반대로 "고쳤다고 기록된 것이 오늘 재발했다"면 그것이 최우선 보고 대상이다(`FixVerificationRecurred` 태그).
4. **커밋 이력** — 당일/최근 커밋이 로그에 실제로 반영됐는가. `status_snapshot.json`의 `code_version.stale`이 true면 커밋은 됐지만 프로세스가 옛 코드로 돌고 있다는 뜻이다.

**다섯 번째 기준이 하나 더 있다 — 오늘 파일의 앞 국면 절.** 장중·장후는 앞 절이 세운 예측과
"확인 필요" 항목을 반드시 채점한다(대원칙 B-②).

국면별 구체 점검항목은 **`references/phases.md`** 에 있다. 반드시 읽고 그 체크리스트를 빠짐없이 통과시킨다.

## 4. 보고서를 쓴다

형식은 **`references/report_template.md`** 를 따른다. **대원칙 A·B가 형식보다 우선한다.**

- **이상점 하나 = 증상 → 근거(로그 인용 + 시각) → 기준 위반(SYSTEM.md 조항/설계 문구) → 영향(평문) → 영향(기술)** 으로 쓴다. 근거 없는 이상점은 쓰지 않는다.
- 심각도는 **P0(오늘 거래에 직접 위험) / P1(정확성·관측 훼손) / P2(운영 부담·기술부채)** 로만 나눈다.
- **불확실한 것은 불확실하다고 쓴다.** "확인 필요"와 "확정된 결함"을 섞지 않는다.
- Fix 계획은 파일 경로·함수 수준까지 내려간다. "로깅을 개선한다"가 아니라 "`src/messiah/data/aggregator.py`의 `_on_tick`에서 늦은 틱을 drop할 때 WARNING+건수 카운터를 추가한다".
- **장전·장중 국면에서는 코드 변경을 제안만 하고 실행하지 않는다** — SYSTEM.md R11 / 금지계명 3·4 (장중 학습 금지·장중 배포 금지). 계획은 세우고 적용은 장후로 미룬다.
- 고도화 방안은 **당일 관측에서 출발**해야 한다. 일반론적 개선 목록은 쓰지 않는다.

산출 위치:

- **보고서: `logs/dailycheck/<YYYY-MM-DD>_report.md` — 하루 한 파일. 장전이 만들고 장중·장후가 append.**
  국면 접미사 파일(`_pre_report.md` 등)을 새로 만들지 않는다.
- 증거 다이제스트는 `logs/dailycheck/evidence_<YYYYMMDD>_<phase>.md` 로 국면별로 둔다.
- Cowork 세션이면 보고서 파일을 `present_files`로 전달한다.
- 채팅 본문에는 **평문 3~5줄**만 쓴다 — 위험 여부 한 줄, 이상점 건수(P0/P1/P2) 한 줄,
  가장 시급한 것과 사용자가 할 일. 전문은 파일에 있다. **채팅 본문에도 대원칙 A가 적용된다.**

## 5. dev_memory에 남긴다 (생략 금지)

SYSTEM.md §7은 모든 세션에 dev_memory 갱신을 의무로 둔다. 점검도 세션이다.

- `dev_memory/DECISION_LOG.md` 에 **append**한다. 형식은 기존 항목과 동일하게 유지하고, 헤딩 첫 단어는 **`[MW0601]`** (PC 식별자)로 시작한다.
- 항목 구성: 증상 → 원인 → 결정 → Why → How to apply → 검증. "라이브 미검증"이면 검증 기한을 명기한다.
- 새로 도출된 fix/고도화 항목은 `dev_memory/NEXT_TODO.md` 에 체크박스로 추가한다.
- **기존 내용을 덮어쓰지 않는다.** 두 파일 다 490~620KB의 누적 기록이다.
- dev_memory는 개발자용이므로 대원칙 A(평문화)를 적용하지 않는다 — **거기서는 정밀함이 우선이다.**
  평문화는 사람에게 보고하는 리포트에만 적용한다.

## 실행을 요청받았을 때

사용자가 "fix 항목 구현해" / "고도화 방안 구현해" 라고 이어서 요청하면:

1. 구현계획을 먼저 항목별로 쓴다 — 변경 파일, 변경 내용, 회귀 위험, 검증 방법.
2. **장전·장중이면 실행하지 않는다.** 계획만 확정하고 장후 적용을 권고한다.
3. 커밋 메시지 첫 단어는 `[MW0601]`.
4. 변경 후에는 `pytest`(해당 범위)와 replay 검증을 거친다 — 금지계명 2.
5. 재시동 여부를 물으면, **재시동 없이 얻는 것(오늘 관측 연속성)과 재시동으로 얻는 것(새 코드 적용)** 을 손익으로 비교해 제시한다. `status_snapshot.json`의 `code_version.stale`이 판단 재료다.
6. 구현 결과는 **그날 파일의 해당 국면 절에 이어 붙인다.** 별도 파일을 만들지 않는다.
