## 1. 재심사에서 뒤집힌 것 (구현 전에 먼저 밝힌다)

### N-1. F-A의 원인 진단은 틀렸다 — 폴백은 `n_experts=0`의 문제가 아니다

12:25 리포트 1-1은 *"`aggregator.py:276`이 `valid_until=None`을 내고 `app.py:140`의 폴백
상수(10초)가 그 자리를 받는다"* 고 적었다. 절반만 맞다.

`ui/data_source.py:99`의 유도식은 이렇다:

```python
cadence = (valid_until - ts_utc).total_seconds()
if cadence <= 0:
    return fallback, None
```

그런데 생산 경로에서 두 값은 **같은 봉의 같은 시각**이다:

| 값 | 실제로 채워지는 것 | 근거 |
|---|---|---|
| `FeatureVector.valid_until` | `bar_open_kst + Horizon길이` = **그 봉의 확정 시각** | `features/engine.py:772` |
| `ExpertView.valid_until` | 위 값 그대로 | `strategy/futures/expert.py:196` |
| `as_of` (= `FuturesView.ts_utc`) | 트리거 `FeatureVector.valid_until` | `strategy/futures/service.py:162` |
| `FuturesView.valid_until` | `min(기여 ExpertView.valid_until)` | `aggregator.py:299` |

`min(...)`은 트리거 자신의 값을 포함하므로 **항상 `as_of` 이하**다. 즉
`cadence = valid_until − ts_utc ≤ 0` 이 **모든 사이클에서 성립**한다 —
`n_experts`가 0이든 5든 상관없다.

`RegimeState`도 같다: `valid_until = bar_confirm_time(bars[-1])`(과거),
`ts_utc`는 발행 시점 wall clock → `cadence` **음수** → 15초 상수.

**결론**: 2026-08-14 F-4가 *"상수 대신 메시지가 스스로 말한 유효기간에서 계산한다"* 며 넣은
유도 경로는 **라이브에서 0회 사용됐다.** 단위 테스트는 통과한다 —
`tests/test_ui_symbol_and_freshness.py:94`의 `_view(1800)`이
`valid_until = ts + 1800`(= 다음 갱신 시각)으로 짓는데, **생산 코드는 그런 값을 만들지 않는다.**
테스트 픽스처가 생산 형상과 다른 전형적 사례다.

같은 이름의 필드에 **두 의미가 공존**하는 것이 근본 원인이다:

- `aggregator.py` 모듈 docstring: *"`valid_until`은 … 그 봉 자신의 확정 시각"* (과거)
- `core/messages.py:372` 주석: *"기여 Horizon 중 가장 이른 **다음 갱신 시각**"* (미래)
- `ui/data_source.py:91` docstring: *"`ts_utc`를 빼면 … **다음 발행까지의 간격**"* (미래)

신선도 계산(`_freshness`)은 **과거** 의미에 의존하므로 그 필드를 바꾸면 집계가 깨진다.
따라서 **F-A를 그대로 구현하면 안 된다** — `valid_until=as_of`를 채워도 `cadence=0`이라
아무것도 달라지지 않는다.

→ **F-A′로 대체**한다(§2 참조).

### N-3. 발행 오프셋 — 12:36 리포트의 수치는 재현되지만, 결론은 절반이었다

**새로 확정된 것 둘**:

1. **3m 이상 전 Horizon의 오프셋 하한이 507~604ms** — `data/bar_composer.py:139`의

   전액 소진**되고, 오후 악화분 약 500ms가 그 위에 얹혀 1,100ms대가 된다.
   → 장후 **J-10/L-7**(p90 1,000ms 초과 시 G-2 재착수) 판정의 실질 근거가 이 표다.
2. **1m 24건의 「경계 이전 발행」(최대 −152.1ms)은 결함이 아니다** — 오늘
   `ClockSkewMeasured`가 *"거래소 시각 − 로컬 시계 = +0.156초"* 다. −152.1ms와 정확히 맞는다.
   봉 확정은 거래소 시각으로 판정하고 로그 `ts`는 로컬 시계라 생긴 그림자다.

**그런데 이 마지막 항목이 F-E의 진짜 근거다**: 로컬 `ts` 프록시만으로는
「59.9초 늦음」과 「0.15초 이름」이 **구분되지 않는다**(초 단위가 되감기므로).
본 분석도 1차 계산에서 정확히 그 함정에 빠졌다가 시계 스큐와 대조해서야 갈랐다.
`FeaturePublish`에 `bar_confirm_kst`가 실리면 이 모호성이 **구조적으로** 사라진다.

  안 듣는 상황이 되기 때문이고, 그때는 원인을 다시 봐야 한다.
- **첫 채점: 08-21 장후 `degenerate_feature_count` 0 복귀.** 기한(08-24)까지 3거래일이라
  `consecutive_days: 3`을 채울 수 있다. 기한 재조정은 필요 없다.

### Q6. 예약 점검 세션과 구현 세션의 dev_memory 충돌

- `messiah-postmarket-check`가 평일 15:50(지터 +429초 → 실제 15:57)에 **빈 세션**으로 떠서
  `DECISION_LOG.md`·`NEXT_TODO.md`에 append한다. 본 세션도 같은 파일을 고친다.
- 오늘은 본 세션이 먼저 끝나도록 순서를 잡았으나, **구조적으로는 두 세션이 같은 누적 파일을
  동시에 고칠 수 있다.** §6 자동화 방안이 이 문제를 다룬다.

## 6. 자동 작업흐름으로 만드는 방안 — 의견

### 결론 먼저

**「종합 재심사·구현계획 수립」까지는 자동화하고, 「구현·커밋」은 자동화하지 않는다.**
그 사이에 **사람이 판정표에 한 줄 회신하는 칸**을 둔다.

### 왜 그렇게 갈라야 하는가 — 오늘의 증거

오늘 네 리포트가 낸 Fix 중 **2건의 전제가 사실과 달랐고, 구현 단계에서 4건이 더 부족했다.**
합쳐서 **6건** — 이 세션이 실제로 한 일의 대부분이 그것이다.

- **F-A**: 「`n_experts=0`이라 폴백을 쓴다」 → 실제로는 **모든 사이클**에서 폴백이었다.
  원안대로 `valid_until=as_of`를 채웠으면 `cadence=0`이라 **아무것도 안 변한 채**
  *"화면 배지 고침"* 커밋이 하나 남았을 것이다.
- **F-4**: 「ps1의 UI 액션에 `2>&1`이 빠졌다」 → 그 파일에 **UI 액션 자체가 없다.**

리포트의 Fix 계획은 파일·함수 수준까지 구체적이어도 **검증되지 않은 가설**이다.
가설을 그대로 구현하는 자동화는 이 저장소가 반복해서 당한 실패 모드
— *"고쳤다는 기록만 남고 새 경로는 한 번도 안 쓰인다"*(오늘 G-A가 세우려는 바로 그 축) —
를 **자동으로, 매일** 재생산한다.

반대로 오늘 §1의 N-1~N-4는 전부 **기계적 대조**로 나왔다: 코드 읽기, 로그 replay,
커밋 이력 조회. 사람의 직관이 필요한 대목이 없었다. **이 부분이 자동화 이득이 큰 곳이다.**

### 제안 구조 — 3단 파이프라인

```
15:50 ① 장후 점검 (기존 예약)              → <날짜>_post_report.md         [자동 · 코드 미변경]
16:10 ② 종합 재심사 (신규 예약)            → <날짜>_synthesis_report.md    [자동 · 코드 미변경]
  ↓   ③ 사람이 판정표에 승인/수정 한 줄     → 회신                          [사람]
  ↓   ④ 구현 세션 (사람이 트리거)           → 커밋 N건 + dev_memory 반영    [반자동]
```

②가 이 세션이 한 일이다. **코드를 한 줄도 안 건드리고 산출이 판정표 하나**라 자동화해도 안전하다.

### ②에 반드시 못 박아야 할 네 가지 (오늘 배운 것)

| # | 규칙 | 오늘 이것이 잡은 것 |
|---|---|---|
| a | **전제 검증을 필수 단계로 둔다** — Fix가 지목한 파일·함수·상수가 실제로 그러한지 코드로 확인한 뒤에만 「구현」 판정을 준다 | F-4 기각 (`install_scheduled_tasks.ps1`에 UI 액션 없음) |
| b | **리포트가 스스로 적은 검증 조건을 실제로 실행한다** | F-E의 replay 요구 → 재현 확인 + 되감기 함정 + 오후 악화 지속 발견 |
| c | **「이미 구현됐는가」를 커밋 이력으로 먼저 대조한다** | G-3 — `4eca9af`가 이미 했다. 안 봤으면 두 번 구현 |
| d | **산출은 판정표 하나로 강제한다** — ID / 이득 / 비용 / 위험 / 판정 / 사유. 「기각·연기」에 사유가 없으면 실패로 친다 | 오늘 §2·§3 표 |

### ④를 자동화하지 않는 이유 — 커밋보다 「라이브 데뷔」가 문제다

커밋은 되돌리기 쉽다. 그러나 오늘 구현분은 **08-21 08:20 기동에서 한꺼번에 첫 실전 노출**된다.
여러 건이 동시에 데뷔하면 무언가 틀어졌을 때 **이분탐색이 안 된다** — 장전 F-1이 정확히 그
이유로 「F 단위 분할 커밋」을 권고했다. 자동 구현은 이 분할 판단을 사람 없이 내리게 된다.

**다만 ④의 앞부분은 자동화해도 좋다**: 변경 적용 → `pytest`(해당 범위) → `ruff` → replay 검증
→ **결과만 보고**. `git commit`만 사람이 누른다. 오늘 기준으로 그 자동화가 아꼈을 시간이 가장 크다.

### 구현 방법 (실무)

1. **스킬을 새로 만들지 않는다.** `messiah-daily-check`에 `--phase synthesis`를 더한다 —
   기준 4곳(SYSTEM.md · 마스터플랜 · dev_memory · 커밋 이력) 대조 절차가 그대로 재사용되고,
   증거 수집기도 그대로 쓴다. 새 스킬을 파면 그 절차가 두 벌이 되어 갈라진다(오늘 G-3의 교훈).
2. `references/schedule_prompts.md`에 **네 번째 블록 「종합 재심사」**를 추가하고
   `messiah-synthesis-check` / `10 16 * * 1-5`로 등록. 장후 실측 기동이 15:57이므로 16:10이면
   지터를 얹어도 ①의 산출을 반드시 본다.
3. **②는 `dev_memory/`에 쓰지 않는다** (Q6 해소). 판정표만 `logs/dailycheck/`에 남기고,
   `DECISION_LOG.md`·`NEXT_TODO.md` 반영은 ④가 한 번에 한다. 누적 300KB 파일을 두 세션이
   동시에 append하면 한쪽이 통째로 날아간다 — 이건 가정이 아니라 파일 크기가 만드는 구조다.
4. ②의 프롬프트에 **「코드·설정을 한 줄도 바꾸지 않는다」를 장전/장중 블록과 같은 강도로 못 박는다.**
   ②는 장후에 도는데, 장후는 이 저장소에서 **유일하게 코드를 고쳐도 되는 국면**이라
   금지 문구가 없으면 모델이 구현까지 진행할 여지가 생긴다.

### 오늘 이 구조가 실제로 작동했다 — 우연히

본 세션은 15:20에 시작해 **①(장후 점검)이 아직 없는 상태에서** ②를 먼저 했다. 그리고
16:05에 예약 ①이 따로 떠서 **P0 1건**(세션 경계 오염)을 냈다 — 본 세션이 §1~§3에서 한 번도
언급하지 않은 것이다. 반대로 본 세션은 ①이 놓친 것을 냈다(F-A의 진짜 원인, G-2 원안의 결함,
git 날짜 필터 함정, G-H의 기본값 위험).

**둘은 겹치지 않았다.** 같은 하루를 다른 순서로 봤기 때문이고, 그것이 ①과 ②를 나누는
근거의 실증이다. 다만 오늘은 순서가 뒤집혀 있었다 — ②가 ①을 채점하지 못했고, 사람이
16:08에 산출된 ①을 손으로 집어넣어야 했다. 제안한 순서(①→②)면 그 수작업이 없다.

**그리고 예상했던 충돌이 실제로 났다**: 예약 ①이 `DECISION_LOG.md`·`NEXT_TODO.md`에 append하는
동안 본 세션도 같은 파일을 고치고 있었다. 오늘은 시차로 피했지만 구조적으로는 매일 가능하다
(Q6). ②가 dev_memory에 안 쓰는 규칙이 필요한 이유다.

### 하지 말 것 — ①과 ②를 한 세션으로 합치기

①은 15:45 배치 산출물을 기다려야 하고, ②는 **①의 결론을 채점**해야 한다.
같은 세션이 자기 결론을 채점하면, 2026-08-19 G-4가 코드로 금지한
**「계기가 자기 자신을 채점한다」를 사람 영역에서 그대로 되풀이**하는 것이다.
오늘 ②가 ①의 전제 2건을 뒤집을 수 있었던 것은 **다른 세션이 다른 순서로 봤기 때문**이다.
